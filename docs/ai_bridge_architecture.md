# pi86-rp2350 Host Bridge Architecture

## Purpose

This document defines the stable architecture for communication between modern host software and native code running on the physical NEC V30.

The first validated host participant was OpenAI Codex, which sent a 64-byte greeting and received a reply generated by the physical V30. That experiment names an accepted endpoint; it does not make Codex, ChatGPT, or AI part of the V30-visible machine model.

The architectural boundary is deliberately provider-neutral:

```text
host program / development tool / optional AI service
                         |
                 Host Bridge API
                         |
              fixed transport records
                         |
               RP2350 companion bridge
                         |
             mailbox / I/O / interrupt / memory
                         |
                  physical NEC V30
```

## A bridge between eras

The endpoints were created roughly forty years apart. They do not share a native vocabulary.

- The V30 understands machine code, interrupts, I/O ports, memory, and physical bus cycles.
- A modern host understands USB records, files, tools, networks, and optional AI services.
- The RP2350 and Host Bridge translate between these domains without pretending the V30 knows what AI is.

To V30 software, the RP2350 is a companion chipset exposing defined machine services. To the host, the bridge exposes structured requests, replies, and physical evidence. AI may interpret, generate, or validate host-side work, but it never participates in a current V30 bus cycle.

## Architectural goals

The bridge shall:

1. preserve the physical NEC V30 as the x86 execution authority;
2. provide a provider-neutral host protocol;
3. keep host and USB latency outside current-cycle bus timing;
4. publish complete V30-visible records atomically;
5. preserve sequence identity across both directions;
6. distinguish application traffic from engineering evidence;
7. fail visibly without unsafe AD-bus ownership;
8. support conventional host programs before requiring an AI integration.

## Non-goals

This architecture does not:

- model AI as a V30 peripheral concept;
- allow an AI model or host process to answer an active V30 bus cycle;
- imply that original 1980s software understands modern host services;
- equate a terminal echo with native V30 execution;
- require Codex, ChatGPT, or any specific model provider;
- hold a V30 cycle open while waiting for a network or host response.

## System boundaries

### Physical V30

The V30 executes native instructions, owns x86 architectural state, and interacts only through ordinary machine mechanisms:

- memory reads and writes;
- I/O reads and writes;
- interrupts and polling;
- buffers and control blocks defined by V30 software.

A newly written BIOS, monitor, driver, or application may use a project-defined companion service. Unmodified historical software can instead interact through a compatible device abstraction such as a serial port, terminal, printer, disk, or conventional BIOS service.

### RP2350 deterministic data plane

PIO and DMA own all qualified current-cycle timing:

- PIO captures current address and control state;
- PIO qualifies and drives deterministic read responses;
- PIO controls AD-bus direction and release;
- DMA transports immutable keys, response descriptors, and passive trace words between SRAM and PIO FIFOs.

No host process, USB callback, AI model, or current-cycle M33 lookup is permitted in this path.

### RP2350 control and service planes

The real-time role prepares and atomically publishes immutable local state, supervises bounded PIO/DMA engines, and records failures. The service role owns USB-facing records, retained trace processing, formatting, and asynchronous interaction with the host.

The role boundary is normative. The numbered Core 0/Core 1 placement may follow SDK and interrupt constraints as long as service work cannot change V30-visible timing.

### Host Bridge

The Host Bridge terminates the USB protocol and exposes complete semantic records to local software. Its responsibilities include:

- device discovery and transport selection;
- framing, sequence numbers, length, and integrity checks;
- timeout, retry, cancellation, and duplicate detection;
- conversion between binary records and a stable program-facing API;
- capture of CDC evidence without treating log text as application data.

The Host Bridge must work with a conventional test program. AI integration is an adapter above this boundary.

### Host-side adapters

Adapters translate a particular client into the provider-neutral Host Bridge API. Examples include:

- Windows or Linux Python tools;
- OpenAI Codex;
- ChatGPT or an OpenAI API application;
- a debugger or trace-analysis tool;
- a file, disk-image, terminal, or automation service;
- another local or remote program.

Provider-specific prompts, credentials, sessions, and response formats terminate in the adapter. They must not appear in the RP2350 or V30-visible ABI.

## V30-visible companion service

The V30 sees a machine service, not an AI service. The current bounded mailbox uses these I/O ports:

| Port | V30 operation | Meaning |
|---:|---|---|
| `00E0h` | read | status and publication state |
| `00E4h` | read | host-to-V30 payload word |
| `00E8h` | write | V30 consumption witness or computation result |
| `00E2h` | write | V30-to-host payload word |
| `00E6h` | write | V30 reply commit |

These addresses describe the accepted bounded implementation. Future BIOS services may wrap the same mechanism with an interrupt or memory control block, but the underlying semantics remain companion-service semantics.

### Status model

The asynchronous service state is conceptually:

```text
IDLE
  -> REQUEST_COMMITTED
  -> HOST_BUSY
  -> RESPONSE_READY
  -> RESPONSE_CONSUMED
  -> IDLE
```

Error states must be explicit:

```text
TIMEOUT
HOST_OFFLINE
BAD_SEQUENCE
BAD_LENGTH
BAD_INTEGRITY
SERVICE_UNAVAILABLE
```

The current HAT holds `READY` high. Therefore host latency is handled by software polling, interrupts between transactions, or later retrieval. A physical bus cycle is never stretched while a host or AI service is working.

### Meaning of a V30-originated request

The V30 cannot request “AI” as a historical concept. It can request a defined companion function, for example:

- write bytes to a host console;
- read a host-provided record;
- obtain time or configuration data;
- load a file or program capsule;
- submit a diagnostic record or register dump;
- request a block from a virtual disk;
- send or receive serial-terminal data.

Host policy may satisfy that request locally, through storage, through a debugger, or through an AI service. That choice is invisible to the V30.

## Transport record

The accepted version 1 USB ABI uses one fixed 64-byte HID record in each direction:

```text
version / type / flags / sequence / length / status / 52-byte payload
```

Version 1 has no CRC or cryptographic integrity field. Its evidence combines exact HID record transfer, sequence and length checks, immutable publication, native V30 witnesses, and independent CDC physical validation. The exact layout and versioning rules are defined in [`companion_service_abi.md`](companion_service_abi.md).

The architectural rules are:

1. incomplete host records are never V30-visible;
2. a sequence is not reused while an earlier transaction is live;
3. publication occurs only after complete-record validation;
4. the reply retains the initiating sequence identity;
5. multi-record messages and new integrity fields require an explicit versioned extension;
6. transport success and native V30 execution evidence are separate results.

## Ownership and publication

Every mutable object has one owner at a time:

```text
host adapter
    -> Host Bridge
    -> RP2350 service role
    -> immutable staging
    -> RP2350 realtime publication
    -> V30 consumption
```

The return path reverses ownership only after the V30 commits a complete reply.

Core-to-core and host-to-device transfer must use bounded queues or explicit ownership handoff. A full queue may drop or reject work according to policy, but it may not block the realtime producer or expose a partial record.

## Canonical host-to-V30 transaction

The accepted greeting is one instance of the general flow:

1. The hardware boots independently of a host session.
2. The physical V30 reaches a polling or service-ready program state.
3. A host adapter submits one complete record through the Host Bridge.
4. The RP2350 service role validates and transfers ownership of that record.
5. The realtime role publishes immutable mailbox state between V30 transactions.
6. The V30 observes `NOT_READY` followed by `READY` through ordinary I/O reads.
7. Native V30 code consumes the record and performs its defined computation.
8. The V30 writes reply words and commits the reply.
9. RP2350 returns one complete transport record to the host.
10. CDC evidence independently proves the physical execution path and terminal state.

For the first accepted Codex adapter, the application payload was:

```text
OpenAI Codex > HELLO NEC V30
NEC V30      > HELLO OPENAI CODEX
```

The greeting is historical validation evidence, not a provider-specific requirement of the architecture.

## V30-originated service transaction

A future V30 BIOS, monitor, or application may initiate a companion request:

1. V30 software prepares a conventional request block or output record.
2. The V30 commits the request through I/O or a defined interrupt service wrapper.
3. RP2350 copies a complete record to the Host Bridge outside the active bus cycle.
4. The host dispatches it to an appropriate local service.
5. The service result is returned as another complete record.
6. RP2350 publishes it atomically.
7. V30 software polls or receives a later interrupt and consumes the result.

An optional AI adapter may interpret a diagnostic record or generate a response, but the V30-visible contract remains unchanged.

## USB channel separation

The composite USB design assigns distinct meanings to its interfaces:

### HID: application records

HID carries fixed binary request and reply records. It is the machine-facing path and must not depend on human-readable console parsing.

### CDC: engineering evidence

CDC is receive-only validation output during accepted bridge operation. It explains why a transaction should be trusted:

- reset and first fetch;
- ROM execution;
- mailbox publication ordering;
- V30 physical I/O reads and writes;
- sequence and integrity witnesses;
- response-deadline results;
- terminal RESET, CLK, and AD-bus state.

HID carries the result. CDC carries the evidence.

## Observability and acceptance

A bridge transaction is accepted only when all required layers agree:

| Layer | Required evidence |
|---|---|
| Host | complete request and reply records with matching sequence |
| USB | correct interface role and complete transfer |
| RP2350 service | ownership handoff and immutable staging |
| RP2350 realtime | atomic publication and bounded engine completion |
| PIO/DMA | qualified pairs completed without deadline miss |
| V30 | native fetch, consumption witness, computation, and reply commit |
| Electrical | safe unsupported cycles and terminal RESET/CLK/AD state |

A visible reply alone is insufficient. Likewise, DMA counters alone do not prove that the V30 consumed the intended data.

## Challenge contract for an AI adapter

An AI adapter is valuable only when it adds reasoning above the stable Host
Bridge without weakening physical acceptance. Its work should be falsifiable
and attributable.

A serious AI-assisted experiment should retain:

- the exact input record, sequence, and integrity identity;
- the hypothesis or generated artifact submitted to the system;
- the expected physical witnesses before execution;
- the immutable firmware, ROM, or capsule identity;
- the V30-produced result;
- the passive bus evidence and first divergence on failure;
- the terminal electrical state;
- the distinction between agent inference and directly observed fact.

Challenge difficulty should grow with the bridge. Replaying a known greeting
proves transport; it does not prove general reasoning. Fresh CRC challenges,
multi-round exchanges, generated native-code capsules, and trace-based fault
diagnosis require the agent to produce work whose physical result was not
prestaged.

The physical V30 remains the execution oracle. The AI adapter may propose and
explain, but it cannot declare its own hardware result successful.

## Growth path

The stable architecture supports progressively richer services without changing the realtime boundary:

1. fresh challenge/response with sequence and CRC;
2. repeated and sustained multi-record exchange;
3. passive trace decoding and first-divergence analysis;
4. fixed-window program or data capsule loading;
5. a V30 monitor and companion-service interrupt wrapper;
6. compatible terminal, serial, disk, keyboard, and display services;
7. optional host-side AI diagnosis, code generation, and trace explanation.

General memory, READY-controlled hardware, active trace replay, and full debugger control are separate architectural capabilities and require their own evidence gates.

## Design summary

```text
V30 side                         Modern side
--------                         -----------
machine code                     host application
interrupt / polling              optional AI adapter
I/O and memory                   Host Bridge API
physical bus                     USB HID records
        \                       /
         \                     /
          RP2350 companion bridge
          PIO / DMA / SRAM
          deterministic publication
```

`pi86-rp2350` does not make a forty-year-old processor understand AI. It gives a physical V30 and a modern host a common, verifiable language while allowing each side to remain native to its own era.
